# 改进代码库架构

像 AI 理解代码一样探索代码库，发现架构摩擦，并提出通过模块加深来改善架构的重构方案，最终形成 GitHub RFC Issue。

**深模块（Deep Module）** 概念来自 John Ousterhout 的《A Philosophy of Software Design》。深模块通过简洁的接口隐藏复杂的内部实现。它更容易测试，也更便于 AI 理解和导航，并允许通过模块边界测试行为，而不是依赖大量内部测试。

## 工作流程

### 1. 探索代码库

使用 Agent 工具和 `subagent_type=Explore` 自然地探索代码库，不要遵循僵化的检查清单。重点关注探索过程中遇到的理解障碍：

- 理解一个业务概念，是否需要在许多零散文件之间反复跳转？
- 模块是否过于浅薄，以至于接口本身几乎和实现一样复杂？
- 是否为了方便测试而抽取了纯函数，但真正的问题却隐藏在函数的调用方式中？
- 紧密耦合的模块是否因接口衔接不清晰而增加了集成风险？

**探索过程中遇到的理解摩擦，就是发现架构改进机会的重要信号。**

### 2. 提出候选方案

按编号列出值得加深的模块，每项说明：

- **涉及模块**：相关模块、文件及业务概念。
- **耦合原因**：共享类型、调用模式或共同承担的业务职责。
- **依赖类别**：参考 `REFERENCE.md` 中定义的四种依赖类别。
- **测试影响**：哪些现有测试可以由模块边界测试替代。

此阶段不要设计具体接口。先询问用户：

**你希望进一步分析哪一个候选方案？**

### 3. 用户选择候选方案

根据用户选择的候选方案，进一步分析模块职责、依赖关系、需要隐藏的内部复杂度，以及预期的调用方式。

### 4. 设计多种接口方案

使用 Agent 工具并行启动至少 3 个子 Agent。每个子 Agent 必须提出一种明显不同的模块接口设计。

向每个子 Agent 提供候选方案的背景，包括模块耦合情况、依赖类别和需要隐藏的复杂度，并分别指定不同的设计目标：

- **Agent 1：极简接口**——尽量将公开入口控制在 1～3 个。
- **Agent 2：灵活可扩展**——支持更多使用场景和扩展能力。
- **Agent 3：优化主要调用场景**——让最常见的调用方式尽可能简单。
- **Agent 4（适用时）：Ports & Adapters**——围绕端口与适配器模式设计跨边界依赖。

每个方案必须说明：

1. **接口定义**：类型、方法、参数及返回值。
2. **调用示例**：展示调用方如何使用该接口。
3. **隐藏的复杂度**：接口内部承担和封装了哪些职责。
4. **依赖策略**：如何处理依赖，参考 [REFERENCE.md](./REFERENCE.md)
5. **优缺点**：主要收益、限制和适用场景。

依次展示各方案，并进行横向比较。

最后给出明确的推荐意见，说明哪个方案最值得采用以及原因。如果不同方案的设计可以互补，可以提出组合方案。

不要只罗列选项，应给出有依据的明确判断。

### 5. 用户确认接口方案

由用户选择最终接口方案，或明确接受推荐方案。

在用户确认之前，不进入 Issue 创建阶段。

### 6. 创建 GitHub Issue

使用 `gh issue create` 创建架构重构 RFC（Request for Comments），并采用  [REFERENCE.md](./REFERENCE.md)中的模板。

创建完成后，将 GitHub Issue 链接提供给用户。
