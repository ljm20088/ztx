# 参考说明（REFERENCE）

## 依赖分类

评估一个候选模块是否适合加深时，需要对其依赖进行分类。

### 1. 进程内依赖（In-process）

纯计算、内存状态，不涉及 I/O。

这类模块始终适合加深，可以直接合并模块并进行测试。

### 2. 可本地替代的依赖（Local-substitutable）

存在本地测试替代方案的依赖，例如：

- 使用 PGLite 替代 PostgreSQL。
- 使用内存文件系统替代真实文件系统。

如果存在可用的测试替代方案，就可以加深模块。在测试套件中运行本地替代实现，对加深后的模块进行测试。

### 3. 自有远程依赖（Ports & Adapters）

跨越网络边界的自有服务，例如微服务和内部 API。

在模块边界定义端口（Port），即接口。深模块负责业务逻辑，传输方式通过依赖注入提供。

- 测试环境：使用内存适配器（In-memory Adapter）。
- 生产环境：使用真实的 HTTP、gRPC 或消息队列适配器。

**推荐方案示例：**

定义一个共享接口（Port），生产环境实现 HTTP 适配器，测试环境实现内存适配器。这样，即使服务部署在不同的网络边界上，业务逻辑仍然可以作为一个完整的深模块进行测试。

### 4. 真正的外部依赖（True external）

不受自己控制的第三方服务，例如 Stripe、Twilio 等。

在依赖边界使用 Mock（模拟对象）。加深后的模块通过注入的端口依赖外部服务，测试时提供 Mock 实现。

## 测试策略

核心原则：**替换，而不是叠加（Replace, don't layer）。**

- 当模块边界测试已经覆盖原有行为后，浅层模块的旧单元测试就不再有保留价值，应删除。
- 在加深后的模块公开接口边界编写新的测试。
- 测试应通过公开接口验证可观察到的结果，而不是检查内部状态。
- 测试应能经受内部重构，不因实现方式变化而频繁修改；测试描述的是行为，而不是实现细节。
