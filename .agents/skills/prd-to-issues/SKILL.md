# PRD 拆分为 GitHub Issues

以 PRD 为唯一需求依据，采用垂直切片（Vertical Slicing）和 Tracer Bullet 方法，将需求转化为可执行任务。

## 工作流程

### 1. 获取 PRD

- 优先使用当前对话中刚生成/确认的 PRD、明确给出的 Issue 编号或 URL；上下文已有完整 PRD 时，不要重复询问用户提供编号。
- 如果只有 PRD 编号且当前上下文没有完整内容，使用 GitHub 工具或 `gh issue view <number>` 获取完整正文及必要评论。
- 不要关闭或擅自修改原始 PRD Issue。

### 2. 检查需求与代码库

- 检查需求完整性、业务规则、验收标准和技术约束。
- 必要时探索代码库，了解现有架构、实现和开发规范。
- 识别已经实现的功能、现有 Issue 和 PR 范围，避免重复拆分或重复建设。
- 发现影响实施的重大歧义时，先向用户确认；成熟技术常规机制直接采用业界实践，不逐项询问。

### 3. 拆分垂直切片

采用 Tracer Bullet（示踪式开发）方法，将需求拆分为可交付的垂直功能切片，而不是按数据库、后端、前端等技术层次机械横向拆分。

拆分原则：

- 每个 Issue 有明确的交付目标和完成条件。
- 尽可能贯穿所需的数据库、API、UI 和测试。
- 粒度适中：一个完整、紧密耦合且需要统一重构/验收的能力可以是一个 Issue；不要为了形式把它拆成多个技术层 Issue。
- 只有存在独立交付价值、明确依赖或可独立验收时才拆成多个 Issue。
- 用户明确要求“生成一个 Issue”或并入指定 PR 时，优先形成一个边界完整的实施 Issue；不要擅自扩展为多 Issue 计划。
- 明确范围和不包含的内容。
- 必要的基础设施、迁移、安全、性能和测试建设可以纳入同一能力切片；只有确实可独立交付时才另建任务。
- 保留 PRD 中 User Story、Acceptance Criteria 和 BDD Scenario 的追溯关系。
- 不重复编写 PRD 已经定义的业务需求。

### 4. 分类与依赖

**HITL / AFK**

- **HITL**：确需人工决策、架构评审、安全批准或人工验收。
- **AFK**：需求明确，可以由 AI 独立实施和验证。
- 分类应反映实际风险和决策需要，不因任务规模大就自动标为 HITL。

**依赖关系**

- 只建立真实的前置依赖。
- 可以并行的任务不应互相阻塞。
- 依赖关系必须构成无环有向图（DAG）。
- 基础任务优先，按照依赖顺序安排实施。
- 必要时创建独立 QA Issue，包含所有需要人工验证的项目及详细验收计划；但不要为每个功能默认增加 QA Issue。

### 5. 用户审核与创建授权

- 先向用户展示任务粒度、依赖关系、类型和范围。
- 用户明确要求“创建 Issue”“按此 PRD 生成 Issue”或已批准本次任务拆分时，该指令即为创建授权，不要再重复询问一次是否创建。
- 用户仅要求分析/规划而未授权创建时，必须等待用户明确批准。
- 若用户明确指定一个 Issue、目标 PR 或现有分支，按指定执行，不另开 PR，不擅自改变交付方式。
- 若拆分方案存在实质性产品边界歧义，先澄清；普通技术细节由实施者按成熟实践处理。

### 6. 创建 GitHub Issues

- 使用可用的 GitHub Issue 工具或 `gh issue create` 创建任务。
- 按照依赖顺序创建，先创建前置任务，以便引用真实 Issue 编号。
- Issue 应引用父 PRD、现有相关 Issue 和指定 PR；不要把父 PRD 的全部内容重复复制进任务。
- 用户要求并入现有 PR 时，在 Issue 中明确目标 PR/分支；实施时沿用该 PR 分支，不创建新的 PR。

## Issue 模板

### Parent PRD
#<prd-issue-number>

### Type
HITL / AFK

### What to build
描述本次完整交付能力，引用 PRD 对应章节，不重复复制完整需求。

### Scope
- 本次包含的内容。
- 明确不包含的内容。

### Acceptance Criteria
- [ ] 验收条件 1
- [ ] 验收条件 2

### Test Strategy
说明适用的 BDD、TDD、单元、集成、API 或 E2E 测试。

### Definition of Done
- [ ] 功能实现完成。
- [ ] 相关测试通过。
- [ ] 必要文档已更新。
- [ ] 验收标准全部满足。

### Blocked by
- Blocked by #<issue-number>

无依赖时填写：None - can start immediately

### Target PR
- PR #<number>（如用户已指定）

### User Stories Addressed
- User Story 1

### BDD Scenarios
引用 PRD 中相关场景，必要时补充任务级测试场景，不改变原始业务规则。

## 7. 核验创建结果

- 确认预期 Issue 均创建成功。
- 检查标题、内容、标签和依赖关系。
- 确认依赖图无循环。
- 检查需求追溯关系是否完整。
- 确认 QA Issue（如有）及其验收范围。
- 确认原始 PRD 未被关闭或擅自修改。
- 用户指定现有 PR 时，确认任务已关联到该 PR 的交付计划。
- 输出 Issue 编号、标题、类型、依赖关系及目标 PR。

## 执行约束

- 不擅自修改或关闭父 PRD。
- 不在用户尚未授权时创建 Issues；明确要求创建即视为授权。
- 不重复拆分已经实现的功能。
- 不制造不必要的技术任务或依赖。
- 不把多个互不相关的业务能力塞入同一个 Issue。
- 不把一个紧密耦合的完整重构机械拆成多个技术层 Issue。
- 所有 Issue 必须有明确的交付目标和可验证的验收标准。
- 未经用户明确批准，不合并 PR、不关闭 Issue。
