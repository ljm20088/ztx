# 生成产品需求文档

将用户的想法转化为结构清晰、可执行、可验收的 PRD。

## 工作流程

1. **理解需求**：明确问题、目标用户、使用场景和预期结果。
2. **调查现状**：必要时探索代码库、文档和现有实现，避免重复设计。
3. **澄清问题**：识别冲突、遗漏和关键歧义；必要时逐一询问用户。复杂设计可使用 `grill-me` 深入讨论。
4. **设计方案**：明确功能范围、模块职责、接口、依赖、数据归属及边界，避免过度设计。
5. **编写 PRD**：按照下方结构整理需求。
6. **审核确认**：检查完整性、一致性和可验收性，交由用户确认后再创建 GitHub Issues。

## 编写原则

- 区分用户明确提出的需、代码库事实、AI 建议和待确认事项。
- User Stories 覆盖关键角色、正常流程、异常流程、权限及业务边界，避免重复堆砌。
- 每个核心需求必须有明确、可验证的 Acceptance Criteria。
- 重要业务行为使用 BDD（Given-When-Then）描述，不强制所有需求采用 Gherkin。
- 模块设计说明职责、接口、依赖、数据归属和测试边界，不强制特定架构或分层模式。
- 按需定义性能、安全、权限、数据一致性、并发、可靠性和可维护性等非功能需求。
- 明确本次范围及不包含的内容。

## PRD 结构

1. **Problem Statement**：背景、问题和目标。
2. **Solution**：整体解决方案。
3. **User Stories**：用户角色、需求和业务价值。
4. **Functional Requirements**：功能需求及业务规则。
5. **Acceptance Criteria**：核心需求的验收标准。
6. **BDD Scenarios**：重要业务行为的 Given-When-Then 场景。
7. **Design Decisions**：模块职责、接口、数据及关键设计决策。
8. **Non-functional Requirements**：非功能需求。
9. **Out of Scope**：本次不包含的内容。
10. **Open Questions**：待确认事项、假设和风险。

根据项目复杂度调整详略，不必为了填满模板而添加无意义内容。

## 输出要求

- 语言清晰、简洁，避免模糊描述和相互矛盾的要求。
- 需求应可追溯、可测试、可验收。
- 不确定的内容明确标记，不擅自替用户做重大决策。
- 先输出完整 PRD 草稿，经用户确认后再创建 GitHub Issues。
- PRD 描述需求和关键设计决策，不负责拆分开发任务或创建 GitHub Issues。
- 后续任务拆分交给 `prd-to-issues`，开发实施交给 `do-work`。
