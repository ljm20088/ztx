# 执行工作

按 Issue 验收标准完成一个工作单元：调查现状、实施、验证并交付。

## 工作流程

### 1. 理解任务

- 阅读 Issue、关联 PRD 和已确认决策；检查依赖是否完成。
- 探索相关代码、模块边界、测试和项目命令。
- 明确范围、验收标准、异常流程及数据/权限边界。
- 只有重大歧义、需求冲突或缺少必要产品决策时才向用户确认；成熟常规机制主动采用可靠实践。

### 2. 实施开发

- 遵循现有架构和技术基线，按最小可交付切片推进，不擅自扩大范围。
- 业务行为采用 BDD 思维；业务规则、缺陷修复、公共工具和基础 UI 组件采用 TDD（Red-Green-Refactor）。
- **每个测试方法都必须在方法声明正上方写中文 BDD 场景注释**，明确前置条件、执行动作和可观察结果，优先使用 Given-When-Then：
  ```kotlin
  // Given：平台管理员已登录，且租户编码尚未使用
  // When：管理员提交合法的租户开通请求
  // Then：系统创建独立数据库并将租户置为可用状态
  @Test
  fun shouldProvisionTenantWithIsolatedDatabase() {
      // 测试准备、执行和断言
  }
  ```
- 测试方法名保持项目正常命名规范，描述被验证的行为；**不要**把 Given/When/Then 或整段场景写进方法名。
- 场景注释不能只写“调用某方法/返回 200”等实现步骤；Then 应描述业务结果，并由断言验证。一个测试方法原则上对应一个清晰场景；参数化测试在方法上说明共同场景及参数差异。类级注释或方法体内零散注释不能替代方法上方的场景注释。
- 测试方法体内仅对复杂准备、关键执行步骤或不明显的断言补充中文注释，避免重复抄写场景。
- 普通页面按风险选择测试方式；重构时保持既有行为测试有效。

### 3. 验证

根据变更风险选择并执行相关验证，不固定为某一组命令：

- 静态检查：类型检查、Lint、格式检查。
- 自动化测试：单元、组件、集成、API、BDD、E2E。
- 构建验证：受影响模块、应用和生产构建。
- 专项验证：数据库迁移、隔离、权限、安全、并发、失败恢复、性能或视觉回归。

优先使用仓库已有命令和 CI。失败后定位、修复并重跑；明确记录未执行、失败或无法验证的项目，不得虚报通过。

### 4. 交付

- 检查完整 diff，清除无关修改；更新必要文档和需求追溯。
- 按用户授权和仓库流程提交代码；未经授权不直接提交主分支。
- 所有验收标准完成并有验证证据后才能关闭 Issue。
- 汇报实现内容、验证结果、PR/提交信息及遗留事项。

## 执行约束

- 不绕过测试、不忽略失败、不伪造验证结果。
- 不擅自修改已确认业务规则或技术基线。
- 发现需求冲突先记录并提出统一建议；不得把实施建议说成用户已确认。
- 一个工作单元完成后再处理下一个。
