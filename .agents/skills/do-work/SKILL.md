# 执行工作

完整执行一个工作单元：理解任务、实施开发、验证结果并交付。

## 工作流程

### 1. 理解任务

- 阅读 Issue、关联 PRD 和相关设计决策。
- 探索代码库，了解现有实现、技术栈和项目约定。
- 检查任务依赖，确认前置任务已完成。
- 确认交付范围和验收标准。
- 遇到重大歧义、需求冲突或缺少必要决策时，先向用户确认。

### 2. 制定计划（可选）

任务复杂时制定简明实施计划，明确实施步骤、影响范围和验证方式。简单任务可以直接执行。

### 3. 实施开发

- 遵循项目现有架构、技术栈和代码规范。
- 按最小可交付切片（Tracer Bullet）逐步实现。
- 遵循 PRD 和 Issue 中的业务规则及验收标准，不擅自改变需求。
- 采用 BDD 思维描述业务行为，在测试代码中使用中文注释说明业务场景及预期行为，优先使用 Given-When-Then（前置条件—执行操作—预期结果）的结构。每个测试方法的 `@Test` 注解之前另写一行中文场景注释；方法体内原有 Given-When-Then 注释保持不变。
- 对业务规则、缺陷修复、公共工具和基础 UI 组件库采用 TDD（Red-Green-Refactor）。
- 普通前端页面根据实际情况选择测试方式。
- 若本技能目录存在 `PROJECT_RULES.md`，执行当前仓库任务前先读取并遵循其中适用的项目规范；该文件不存在时跳过。
- 重构时确保原有测试持续通过。

### 4. 验证

根据变更范围和风险选择验证方式：

- 静态检查：类型检查、Lint、格式检查。
- 自动化测试：单元、组件、集成、API、BDD、E2E。
- 构建验证：相关模块和生产构建。
- 专项验证：数据库迁移、安全、权限、性能和视觉回归。

优先使用项目已有的验证命令和 CI 检查。失败后修复并重新验证。

不得虚报结果；明确报告未执行、失败或无法验证的项目。

### 5. 提交与交付

- 检查代码差异，清除无关修改。
- 按项目规范提交；未经授权不提交代码。
- 更新必要文档和 Issue 状态。
- 汇报实施内容、验证结果、遗留问题及提交信息。
- 所有约定任务和验收条件完成后，才能标记为完成。

## 执行约束

- 不擅自扩大 Issue 范围。
- 不绕过已有测试或忽略失败结果。
- 不擅自修改已确认的业务规则。
- 发现 PRD 或 Issue 存在错误时，先记录并确认处理方式。
- 未完成的工作如实说明，不得标记为已完成。
- 一个工作单元完成后，再处理下一个工作单元。
