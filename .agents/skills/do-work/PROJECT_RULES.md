# ZTX 项目开发规范

本文档是 ZTX 项目对通用 `do-work` 工作流程的补充。执行本仓库任务时，必须同时遵循本文件；如与通用技能冲突，以本项目已确认的 PRD、设计决策和本文件为准。本文档只存放 ZTX 专属约束，不修改或扩展通用技能本身。

## 1. 代码实现原则

- **UI 组件优先，精简代码为荣。** 所有业务页面必须优先使用 ZTX UI 组件；页面可以编写业务布局和业务专属展示，但不得重复实现已有的基础控件或通用交互。前后端开发均应优先复用已有能力，保持实现简洁，避免重复代码、无必要的抽象和过度设计。
- 前端基础控件统一通过 `@ztx/ui` 使用；缺少通用能力时，优先补充或完善 ZTX UI 组件，再由业务页面组合使用。
- 页面可以保留业务专属布局、业务信息展示和导航行为；不要为了抽象而把一次性业务展示强行组件化。
- 样式遵循 Tailwind CSS + ZTX Design Tokens：Tailwind utility classes 是布局和常规样式的默认实现方式；Design Tokens 是颜色、字号、间距、圆角等视觉参数的统一来源。
- 不得在业务页面随意硬编码设计令牌已管理的视觉参数。复杂伪元素、特殊动画、复杂选择器或 Tailwind 不适合表达的局部样式，可以使用原生 CSS，并保持范围局部、理由明确。
- ZTX 基座阶段必须完成现有核心页面和共享 UI 组件的样式统一迁移，不以旧页面长期保留原生 CSS 作为默认策略；迁移应保留已确认的页面布局、导航交互和业务行为。
- 复用现有依赖和平台能力，不引入重复库、无必要的架构层或过度设计。新增依赖应说明现有能力为何不能满足需求。

## 2. 测试约定

- 采用 BDD 思维描述业务行为；测试代码中的业务场景及预期行为使用中文注释，优先使用 Given-When-Then（前置条件—执行操作—预期结果）结构。
- 每个测试方法的 `@Test` 注解之前另写一行简短中文场景注释；方法体内原有 Given-When-Then 注释保持不变，不把它们移到方法名或替换成英文方法名。
- 对业务规则、缺陷修复、公共工具和基础 UI 组件库采用 TDD（Red-Green-Refactor）。
- 普通前端页面根据实际风险和变更范围选择测试方式；优先复用现有 Vitest、组件测试和 Playwright 测试设施。
- 重构时确保原有测试持续通过；不得为了通过测试而删除有效断言或绕过行为验证。

## 3. 前端技术边界

- 使用 Vue 3、TypeScript、Vite 和 pnpm Workspace。
- Tailwind CSS 是实际使用的样式工具基础，不应仅安装插件而继续将原生 CSS 作为所有页面的默认样式实现。
- ZTX Design Tokens 通过 CSS Variables 定义，并映射到 Tailwind 语义化工具类；避免建设庞大或复杂的设计系统。
- `@ztx/ui` 是业务页面使用基础组件的统一入口；Reka UI 用于无样式交互原语；Lucide 是统一图标来源。
- shadcn-vue 仅作为源码和实现思路参考，不作为运行时组件库依赖；借鉴或复制的代码由 ZTX 自行维护。
- 表格逻辑按产品需求采用 TanStack Table；不要把简单 HTML Table 样式包装误认为已实现 TanStack Table 能力。
- 字体按产品需求本地部署并提供系统回退，不依赖在线 CDN。
- 不直接绑定 Element Plus 等完整第三方 UI 框架。

## 4. 规范适用与演进

- 本文档只记录 ZTX 项目约束；通用执行流程、计划、验证和交付要求仍由 `SKILL.md` 负责。
- PRD、经用户确认的设计决策或 Issue 对某项能力有更具体的范围和阶段要求时，按其明确范围实施，不擅自扩大本次任务。
- 发现规范与实际代码不一致时，区分“规范未落实”“规范本身需调整”和“尚未进入当前交付范围”，通过 Issue 跟踪，不以静默偏离代替决策。

## 5. Pull Request 交付与验收纪律

- 每个 Issue 或明确工作单元单独建立功能分支和 Pull Request；不得把多个互不依赖的 Issue 混成一个 PR。
- 开发完成后创建 PR，默认保持 Open 状态，不自动合并；CI 通过不等于用户验收通过。
- PR 创建后必须等待用户在 GitHub 检查代码并进行实际测试。用户明确回复可以合并之前，不得执行 Squash merge、Merge commit、Rebase merge，不得关闭对应 Issue，也不得把 PR 转为已完成。
- 用户批准后，只合并本次已批准的那个 PR；合并方式固定为 **Squash and merge**，使每个 PR 在 `main` 上只产生一个提交。
- 一个 PR 验收和合并完成后，再开始依赖它的下一个 Issue；若用户明确要求并行实施，则仍分别创建 PR，并保留各自的验收门禁。
- PR 描述必须列出关联 Issue、实现范围、验证命令及真实结果、未完成项和人工验收步骤；不得虚报本地或 CI 测试结果。
- 不直接向 `main` 推送开发提交，不擅自覆盖用户分支或重写已发布历史。
