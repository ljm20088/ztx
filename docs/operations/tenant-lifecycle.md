# 租户数据库开通与运维

平台控制面数据库保存租户注册信息、生命周期状态、数据库名称路由和开通任务。每个租户使用独立 PostgreSQL 数据库；租户库只运行 `database/tenant-migrations` 下的迁移，不运行平台管理员及控制面迁移。

## PostgreSQL 权限

ZTX 连接控制面数据库所使用的 PostgreSQL 角色必须具有：

- 连接控制面数据库的权限；
- `CREATEDB` 权限，以便开通流程创建租户数据库；
- 对新建数据库执行 DDL、Flyway 迁移及初始化数据写入的权限。

租户数据库目前沿用应用数据库连接配置中的主机、端口、用户名和密码，数据库名由服务端生成。不要接受浏览器传入数据库名、主机、用户名或密码。

## 开通流程

1. 平台管理员在平台控制台创建租户，提交唯一租户编码和名称。
2. 控制面创建租户记录和开通任务，并取得短期执行租约。
3. 服务端创建独立 PostgreSQL 数据库，执行租户迁移并写入租户信息。
4. 服务端生成 24 小时有效的一次性租户管理员初始化凭据；凭据仅以哈希形式保存在租户库，明文只在本次成功响应中返回。
5. 全部步骤成功后，控制面才将租户标记为 `ACTIVE`。失败时记录错误并标记为 `FAILED`，不会显示为可用。
6. 平台管理员将一次性凭据交付给租户管理员；租户管理员通过租户登录页的首次设置入口调用 `POST /api/v1/tenant/auth/setup`，提交租户编码、凭据、账号和密码，设置首个租户管理员并自动建立登录会话。密码至少 8 位且同时包含字母和数字。凭据消费与管理员创建在同一事务中，不能重放。

同一租户编码重复提交会命中既有记录，不会创建第二个租户数据库。失败记录可由平台管理员重试；已存在的数据库会先执行 Flyway 校验/迁移，再继续初始化。

## 生命周期

- `ACTIVE`：允许服务端解析该租户的数据库路由。
- `INACTIVE`：平台管理员停用后，服务端不再返回该租户的活动数据库路由。
- `FAILED`：开通失败，可诊断后重试。
- `PROVISIONING`：正在开通；执行租约过期后允许安全重试。

租户开通、失败、启用和停用均写入控制面审计记录。租户数据库与控制面数据库分离，租户业务身份不写入平台管理员表。


## 租户登录与会话

- 租户用户通过租户登录页提交租户编码、用户名和密码；平台管理员登录入口独立，不与租户账号共用身份或会话。
- 登录、当前会话、退出和密码修改接口分别为 `POST /api/v1/tenant/auth/login`、`GET /api/v1/tenant/auth/me`、`POST /api/v1/tenant/auth/logout` 和 `POST /api/v1/tenant/auth/password`。
- 首次管理员设置成功后自动登录。密码至少 8 位且同时包含字母和数字；修改密码需要当前密码，其他活动会话随即撤销。
- 会话令牌使用随机不透明值；租户数据库只保存令牌 SHA-256 摘要。浏览器使用 HttpOnly、SameSite=Strict Cookie，默认有效期 8 小时；服务端同时检查数据库过期时间和撤销状态。
- 同一租户连续登录失败达到 5 次后，对该账号/IP 组合锁定 15 分钟；失败响应不区分租户不存在、账号不存在或密码错误。
- 每次租户 API 请求都先从控制面确认租户处于 ACTIVE，再使用服务端登记的数据库名称选择租户连接池，并在该租户数据库验证会话。客户端请求头、查询参数、请求体中的租户或数据库字段不作为路由依据。
- 后台任务在控制面任务记录中携带 tenant_id；Worker 执行前重新查询控制面并验证租户状态，随后构建可信租户任务上下文。
