# ZTX 数据库总体设计需求 V1.0

## 一、建设目标

建立简单、稳定、易维护、可扩展的数据库架构，满足制造业 ERP 的多客户、多账套、跨年度查询、客户自定义字段及长期数据增长需求。

设计原则：

- 结构清晰，优先使用 PostgreSQL 原生能力。
- 标准业务数据采用明确的关系表，不采用全局 EAV 模型。
- 初期保持简单，避免过度设计。
- 根据实际数据规模和性能指标逐步扩展。

## 二、总体架构

### 1. 客户数据隔离

- 每个客户使用独立 PostgreSQL 数据库。
- 初期允许多个客户数据库部署在同一 PostgreSQL 集群。
- 客户之间的数据、权限和访问必须隔离。

### 2. 逻辑账套

- 一个客户数据库可以包含多个逻辑账套。
- 账套是业务管理概念，不使用独立数据库或 Schema 表示。
- 业务数据根据实际管理需要关联账套。
- 基础档案是否跨账套共享，由档案类型和业务规则决定，不默认全部共享。

### 3. 年度与会计期间

- 年度、会计期间属于业务管理概念，不按年度复制数据库、Schema 或业务表。
- 通过业务日期、账套及会计期间管理年度数据。
- 支持跨年度查询。
- 年结负责业务期间结转和状态管理，不等同于数据归档。

## 三、Schema 与表命名

### 1. Schema 组织

按业务模块划分 Schema，例如：

| **Schema** | **业务范围** |
|---|---|
| platform | 平台基础 |
| iam | 用户与权限 |
| audit | 审计 |
| meta | 元数据 |
| base | 基础档案 |
| pur | 采购 |
| sal | 销售 |
| inv | 库存 |
| mfg | 生产 |
| quality | 质量 |
| cost | 成本 |
| fin | 财务 |
| custom | 自定义扩展 |

### 2. 表命名

Schema 已经表示业务模块，表名不再重复模块前缀。

正确示例：

- base.material
- base.customer
- pur.purchase_order
- pur.purchase_order_line
- sal.sales_order
- inv.stock_transaction
- mfg.production_order
- cost.batch_settlement

命名规则：

- 表名和字段名统一使用 snake_case。
- 主键默认使用 id。
- 外键使用业务实体名称加 _id，例如 material_id。
- 不使用 pur.pur_purchase_order 这种重复命名。

## 四、标准数据与客户自定义字段

- 标准业务字段放在标准业务表中。
- 客户自定义字段使用独立扩展表，不直接修改标准业务表结构。
- 扩展字段需要有元数据定义，支持字段类型、显示配置、校验和权限控制。
- 根据查询、索引和存储需求选择合适的数据结构，不强制所有自定义字段采用同一种存储方式。
- 自定义字段必须纳入数据权限、脱敏、审计和升级兼容管理。

## 五、基础档案管理

- 基础档案使用稳定的业务 ID。
- 已被业务单据引用的档案原则上不直接物理删除，优先停用。
- 修改重要档案信息时，应保留必要的历史版本。
- 历史业务必须能够正确还原当时使用的关键档案信息。
- 不通过每年复制一套基础档案解决历史查询问题。

## 六、数据表与分区策略

- 初期优先使用普通 PostgreSQL 物理表。
- 不要求所有业务表预先分区。
- 当流水数据规模和查询性能达到实际瓶颈后，再评估分区表。
- 优先评估库存流水、生产记录、质量检验记录等持续增长的大表。
- 基础档案、普通配置表和库存余额表原则上先使用普通表。
- 引入分区前必须验证主键、唯一约束、外键、索引和查询兼容性。
- 分区必须有明确的性能或维护收益，不能仅为了技术先进而引入。

## 七、历史数据与归档

- 跨年度查询优先使用统一业务数据模型。
- 年结和数据归档分别设计、分别管理。
- 初期不建设独立归档数据库。
- 后续根据数据规模、查询频率、存储成本和合规要求决定是否归档。
- 归档后必须明确查询权限、数据恢复和历史追溯方式。

## 八、实施要求

| **阶段** | **实施内容** |
|---|---|
| S0 | 建立数据库 Schema、命名规范及基础迁移机制 |
| S1 | 实现客户数据库隔离、逻辑账套、年度和期间管理 |
| S2 | 实现基础档案、扩展字段、历史版本和跨年度查询 |
| S3 | 完善数据权限、审计、性能监控及分区扩展能力 |

## 九、验收要求

- 不同客户的数据严格隔离。
- 一个客户数据库支持多个逻辑账套。
- 年度和会计期间不依赖复制数据库或业务表实现。
- 支持跨年度业务查询。
- Schema 与表名遵循统一命名规范，不重复模块前缀。
- 标准字段与客户自定义字段分离。
- 基础档案停用后，历史业务仍可正确查询。
- 普通表能够满足初期业务需求。
- 分区表可以在后期按需引入，不影响整体业务模型。
- 年结、归档和历史数据查询具有明确的权限与审计机制。

## 十、明确不采用的方案

- 不按客户年度复制整套业务表。
- 不把账套设计成独立 Schema。
- 不把年度管理等同于数据归档。
- 不要求所有表一开始就使用分区。
- 不采用全局 EAV 表存储所有标准业务数据。
- 不在标准表名中重复 Schema 的模块前缀。
- 不因停用基础档案而破坏历史业务数据。
