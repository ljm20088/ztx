# ZTX 低代码业务开发规范与运行时需求

**文档版本：** V1.0\
**文档类型：** 总体需求与架构规范\
**项目：** ZTX 制造业低代码 ERP\
**状态：** 需求基线草案

------------------------------------------------------------------------

## 1. 文档目的

本文定义 ZTX
低代码业务开发平台的总体目标、开发原则、业务开发模式、运行时职责及验收要求。

本文回答三个问题：

1.  ZTX 希望为业务开发者提供什么样的开发体验？
2.  元数据、Document、Kotlin 业务代码和 Ability Runtime
    分别承担什么职责？
3.  平台最终需要具备哪些能力，才能支持制造业 ERP 的简单业务与复杂业务？

本文是总体需求文档。元数据发布、编译执行计划等具体技术机制由配套专项设计文档细化，不在本文中重复规定实现细节。

## 2. 项目目标

ZTX 建设一套面向制造业 ERP 的低代码开发平台。开发体验参考
Frappe/ERPNext，借鉴 MuYunSpring 的 Ability 运行时思想，结合 Kotlin
的强类型能力和 PostgreSQL 的事务及数据管理能力。

核心目标：

> 普通业务尽量通过元数据完成定义；常规单据通过少量 Kotlin
> 代码扩展；复杂制造业务保留明确、可测试的 Kotlin
> 实现；框架自动提供通用运行时能力。

ZTX 不应成为要求开发者为每个业务编写多层样板代码的传统 CRUD
框架，也不应成为只能通过配置表达业务的封闭低代码平台。

## 3. 总体开发原则

### 3.1 默认一个业务一个文件

-   默认以业务对象为组织单位。
-   普通单据的字段数据结构、校验逻辑和业务动作可以集中在一个 Kotlin
    文件中。
-   不强制采用 Model、Service、Repository、Controller 四层结构。
-   只有代码规模、复用边界或团队协作确实需要时，才拆分文件和模块。
-   不得为了追求"一个文件"而把不相关职责强行塞在一起。

### 3.2 Document 同时承载单据数据和单据行为

Document 是常规业务单据的核心编程模型，可以承载：

-   单据数据结构及明细集合。
-   单据级校验。
-   保存、提交、撤销等生命周期扩展。
-   生成下游单据等明确业务动作。

框架负责 Document 的通用持久化、生命周期调度和运行时接入。

Document 不等于所有业务逻辑的容器。MRP 运算、BOM
展开、生产排程、复杂库存处理、成本结算等可以采用独立 Kotlin
业务实现，不要求继承 Document。

### 3.3 元数据负责通用业务描述

元数据用于描述适合配置化的通用信息：

-   DocType / 业务对象标识。
-   字段名称、类型、默认值、必填、只读等属性。
-   字段关联及引用目标。
-   表单布局、控件和展示规则。
-   列表列、筛选、排序和搜索配置。
-   角色权限声明。
-   可配置的简单校验及展示条件。
-   元数据版本和发布状态。

元数据描述业务结构和通用行为，不应替代复杂制造业务算法。

### 3.4 Ability 由运行时自动组合

Ability 是运行时提供的横切能力，不要求业务开发者手动编排底层执行管道。

典型 Ability 包括：

-   身份与权限检查。
-   租户、账套、部门、工厂等数据范围检查。
-   字段级权限、脱敏和数据过滤。
-   参数及字段校验。
-   事务管理。
-   审计记录。
-   编码规则。
-   生命周期事件。
-   可靠事件发布及异步任务接入。

业务开发者通过正常的 Document
操作或业务入口触发运行时；运行时根据业务定义、请求上下文和策略组合所需
Ability。

Ability
不能取代明确的业务模块。库存、采购、生产、成本等领域能力应保留清晰的业务语义和调用边界。

### 3.5 复杂业务允许直接编写 Kotlin

以下业务应允许使用明确的 Kotlin 代码实现：

-   BOM 多层展开。
-   MRP 物料需求计算。
-   生产排程及产能计算。
-   生产领料、退料及批次处理。
-   批次实际成本计算和后续成本结算。
-   财务期间关账及历史数据治理。
-   复杂跨单据事务和并发控制。

低代码的目标是减少重复开发，而不是把所有算法改造成配置表达式。

### 3.6 只有真正复杂时才拆分

拆分代码应由真实复杂度驱动，例如：

-   独立的复用边界。
-   不同事务边界。
-   独立的并发或性能要求。
-   明确的领域边界。
-   需要单独测试或由不同团队维护。

不得将固定四层结构作为新增业务的强制模板。

### 3.7 复杂查询允许直接 SQL

-   复杂报表、统计和查询允许直接编写 SQL。
-   查询结果可以直接返回 JSON，不强制创建 DTO。
-   不强制每条查询都经过 Repository。
-   SQL 必须使用参数化方式，禁止拼接不可信输入。
-   直接 SQL 不能绕过租户、账套、部门、工厂等数据范围和字段权限。
-   查询与命令应根据实际需要采用不同实现方式，不要求所有查询都经过
    Document 生命周期。

### 3.8 Kotlin 类型安全

-   HTTP JSON 请求由统一序列化层转换为 Kotlin 强类型对象。
-   嵌套明细应自动转换为 `List<Line>` 等类型。
-   统一配置 Jackson Kotlin Module 和 Java Time
    支持，或采用经项目确认的等效方案。
-   业务代码不应普遍直接操作原始 JSON 节点。
-   输入转换、字段校验和业务校验应有清晰的错误反馈。

## 4. 业务开发模式

ZTX 至少支持以下三种模式。

### 4.1 纯元数据业务

适用于设备档案、工装夹具档案、简单基础资料和轻量申请单等。

开发者定义字段、表单、列表和权限元数据，不需要编写 Kotlin
业务类。运行时提供通用 CRUD、页面和 API。

### 4.2 元数据 + 单个 Kotlin 业务文件

适用于采购订单、销售订单、一般库存单据等常规单据。

元数据描述字段、页面和权限；Kotlin
文件定义强类型数据、校验和业务动作。框架自动接入持久化、生命周期和横切能力。

推荐的目标目录形态：

``` text
purchase_order/
├── purchase_order.yaml
└── PurchaseOrder.kt
```

以上是建议的组织形式，不代表必须采用特定目录名或文件名。

### 4.3 Kotlin 专用业务实现

适用于 MRP、BOM 展开、排程、批次成本结算等计算密集或规则复杂的业务。

这类业务可以使用普通 Kotlin 类、函数或任务入口，不强制继承
Document。它们仍应通过统一运行时边界获得必要的权限、事务、审计、追踪和任务治理能力。

## 5. 目标架构及职责边界

### 5.1 业务开发层

包含：

-   元数据定义。
-   Document 业务对象。
-   Kotlin 业务方法。
-   专用业务计算和查询。

### 5.2 元数据运行时

负责：

-   元数据加载、解析、校验和版本管理。
-   元数据编译结果的管理。
-   Document 与元数据的关联。
-   通用 CRUD 和生命周期调度。
-   REST API 接入。
-   表单、列表和详情页面描述。
-   运行时缓存和版本切换。

元数据发布时的编译执行计划由《ZTX 元数据发布与执行计划编译设计》规定。

### 5.3 Ability Runtime

负责：

-   根据请求上下文、业务定义和策略组合横切能力。
-   统一执行权限、数据范围、校验、事务、审计等能力。
-   统一处理失败、回滚、追踪和执行顺序。
-   避免业务开发者重复编写通用基础设施代码。

### 5.4 基础设施层

包括
Kotlin、Vert.x、PostgreSQL、序列化、数据库连接池、迁移工具、日志、监控和消息基础设施。

## 6. Document 目标 API 形态

以下代码用于说明期望的开发体验，是目标 API
示意，不代表当前代码仓库已经实现这些接口。

``` kotlin
class PurchaseOrder : Document<PurchaseOrder.Data>() {

    data class Data(
        var supplierId: UUID,
        var orderDate: LocalDate,
        var items: List<Item>,
        var status: String = "DRAFT"
    )

    data class Item(
        var materialId: UUID,
        var quantity: BigDecimal,
        var unitPrice: BigDecimal
    )

    override suspend fun validate() {
        require(data.items.isNotEmpty()) {
            "采购订单至少需要一条明细"
        }

        require(data.items.all { it.quantity > BigDecimal.ZERO }) {
            "采购数量必须大于零"
        }
    }

    suspend fun submit() {
        require(data.status == "DRAFT") {
            "只有草稿可以提交"
        }

        data.status = "SUBMITTED"
        save()
    }
}
```

目标要求：

-   数据定义和常规单据行为可以集中在一个文件。
-   明细使用强类型集合。
-   生命周期方法由框架按约定调用。
-   业务动作由框架提供受控入口。
-   `save()` 等框架操作自动接入必要的 Ability。
-   复杂动作可以显式调用库存、采购、生产等业务能力。
-   不允许通过绕过运行时的方式破坏权限、事务或审计边界。

## 7. JSON 到 Kotlin 类型的转换

前端提交的 JSON 应由统一序列化层转换为业务数据类型。

示意：

``` kotlin
val data = objectMapper.readValue(
    requestBody,
    PurchaseOrder.Data::class.java
)
```

对于嵌套明细，序列化层应将 `items` 自动转换为
`List<PurchaseOrder.Item>`，并正确处理 UUID、LocalDate、BigDecimal
等类型。

正式实现需要统一配置 Kotlin 和 Java Time
模块，并对未知字段、缺失字段、类型错误和数值精度制定一致策略。

## 8. 业务动作、生命周期和跨模块调用

-   生命周期方法用于通用且稳定的单据阶段扩展，例如校验、保存前处理、提交后处理。
-   用户触发的业务动作应具有明确名称和权限，例如
    `submit`、`cancel`、`makeReceipt`。
-   不应把所有业务流程都塞进 `on_submit` 等生命周期方法。
-   跨模块操作必须明确调用语义、事务边界和失败处理。
-   生成下游单据时，应保留来源单据、来源明细和数量关系。
-   异步事件应使用可靠发布机制，避免数据库提交成功但事件丢失。

## 9. 制造业业务边界要求

低代码框架不得弱化制造业核心业务规则。

### 9.1 库存与成本分离

库存管理和成本管理保持独立模块边界。库存记录数量、位置、批次和库存状态；成本模块负责成本归集、分配、结算和追溯。

### 9.2 批次实际成本

成本模型应支持批次实际成本、后续成本结算和成本版本追溯。不得将批次实际成本简单替换为无法解释实际批次差异的统一平均值。

### 9.3 关账与历史修正

已关闭期间的数据修正必须经过授权、保留版本和审计轨迹，不得静默覆盖历史数据。

### 9.4 年度与归档

跨年度查询、历史年度归档和基础档案身份关联应由数据库及业务架构统一保障，不能依赖元数据动态字段解决。

## 10. 安全、数据一致性和可运维要求

-   所有业务入口必须经过身份认证和权限检查。
-   数据范围必须在服务端强制执行，不能只依赖前端隐藏按钮。
-   直接 SQL 必须遵守统一数据访问安全约束。
-   事务边界由运行时或明确的业务事务入口控制。
-   审计记录应明确哪些操作必须与业务事务同成同败。
-   并发更新应采用版本号、锁或其他明确机制。
-   元数据和业务代码的版本关系必须可追溯。
-   运行时计划、业务版本和请求应具备可观测性。
-   发布失败不得影响当前有效版本。

## 11. 分阶段实施建议

### S0：开发模型基础

-   明确元数据模型和 Document 基础 API。
-   完成 Kotlin JSON 类型转换。
-   建立业务对象注册机制。
-   验证一个业务一个文件的目标开发体验。

### S1：元数据驱动基础能力

-   通用字段类型和字段校验。
-   元数据驱动 CRUD。
-   表单、列表和详情描述。
-   基础 REST API。
-   基础权限声明。

### S2：统一运行时能力

-   Ability Runtime。
-   权限和数据范围。
-   事务和审计。
-   Document 生命周期。
-   业务动作执行入口。
-   统一错误处理和追踪。

### S3：发布治理和扩展能力

-   元数据发布与编译执行计划。
-   元数据版本管理和回滚。
-   元数据与 Kotlin 业务实现绑定。
-   统一页面描述符。
-   扩展字段和业务扩展机制。
-   完整的安全、性能和可靠性验收。

阶段划分是实施建议，实际执行顺序应以项目现有基线和依赖关系为准。

## 12. 总体验收标准

1.  简单档案可以仅通过元数据定义和运行。
2.  普通单据默认不需要 Model、Service、Repository、Controller 四层代码。
3.  普通单据可以在一个 Kotlin 文件中定义数据、校验和常规业务动作。
4.  嵌套 JSON 明细能自动转换为 Kotlin 强类型集合。
5.  通用 CRUD、REST、表单和列表由运行时提供。
6.  权限、数据范围、事务和审计由运行时统一接入。
7.  复杂制造业务可以直接使用 Kotlin 实现。
8.  复杂查询可以直接 SQL，但不能绕过安全边界。
9.  元数据具备版本、发布、回滚和运行时一致性保障。
10. 库存、成本、批次和关账等核心制造业务保持明确边界和可追溯性。

## 13. 与专项设计文档的关系

本文是总体需求和架构原则基线。

《ZTX
元数据发布与执行计划编译设计》是本文中"元数据运行时、发布治理和版本管理"部分的专项技术设计，负责进一步定义：

-   元数据解析与标准化。
-   静态校验和依赖分析。
-   DocumentPlan 等执行计划结构。
-   编译结果存储与缓存。
-   元数据发布和原子切换。
-   版本兼容、失败恢复和回滚。
-   编译计划与 Kotlin 业务实现的绑定。

专项设计不得改变本文确立的开发原则；若发现总体原则存在缺陷，应先修订总体需求，再同步修订专项设计。
