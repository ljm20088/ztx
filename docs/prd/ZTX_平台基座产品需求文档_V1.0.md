## 1. Problem Statement

### 1.1 背景

ZTX 面向制造业，目标是建设一套兼具 ERP 业务能力与低代码开发能力的平台。产品开发体验借鉴 Frappe/ERPNext 的元数据驱动思想，并结合 Kotlin 的强类型能力、PostgreSQL 的事务与数据管理能力，以及制造业 ERP 对业务数据、批次、成本和审计的要求。

传统 ERP 开发往往存在大量重复 CRUD、表单、列表、权限和流程样板代码；纯配置式低代码又难以承载复杂制造算法和严格的数据一致性要求。ZTX 需要在两者之间建立清晰边界：普通业务尽量元数据化，常规单据可用少量 Kotlin 扩展，复杂业务允许直接 Kotlin 实现。

### 1.2 当前问题

当前仓库仍处于平台基座建设阶段，需要先形成可运行、可测试、可持续演进的工程和运行时基础。若直接开发完整制造业务，容易在租户隔离、组织和账套模型、权限、元数据版本、运行时和扩展治理尚未稳定时产生返工。

### 1.3 产品目标

在 S0–S3 建成可用于后续制造 ERP 模块开发的平台基座，使平台开发团队能够：

1. 通过元数据定义常规业务对象、字段、表单、列表和权限。
2. 通过 Document 统一承载常规单据数据和生命周期行为。
3. 通过 Kotlin 文件实现需要强类型和明确业务逻辑的单据。
4. 对复杂计算和制造业务直接采用 Kotlin 专用实现。
5. 通过统一 Ability Runtime 获得权限、数据范围、事务、审计等横切能力。
6. 通过元数据发布、版本管理和 RuntimeSnapshot 保证运行时一致性。
7. 允许租户在受控边界内配置字段和编写 Hook，而不能修改平台核心运行时。
8. 以离线可部署、可自动化测试、可观测和 AI 友好的工程方式交付。

### 1.4 成功指标

- 可在开发环境和离线私有化环境启动平台。
- 可创建平台管理员、开通租户并初始化租户管理员。
- 不同租户的业务数据、账号、权限和会话严格隔离。
- 可通过岗位和模块角色正确授予并执行权限。
- 可通过元数据创建并运行基础业务对象、表单和列表。
- 租户可增加自定义字段；字段具有独立物理列，可查询、筛选、排序和索引。
- 元数据可版本化发布、回滚，多实例切换时请求不混用版本。
- Hook 在受控环境执行，失败行为、事务和异步重试符合定义。
- 核心场景有可重复执行的自动化测试。

## 2. Solution

### 2.1 产品范围

本次建设平台基座，不交付完整制造业务。S0–S3 主要建设：

- 工程、部署和运行基础。
- 多租户、企业、账套、组织、用户、员工、岗位和权限。
- 元数据、Document、表单、列表、查询和自定义字段。
- 元数据发布、RuntimeSnapshot 和版本治理。
- Hook、工作流、编号、文件、通知、导入导出、后台任务等通用服务。
- 安全、审计、国际化、可观测性和自动化测试。

### 2.2 核心产品原则

1. **平台与租户职责分离：** 平台团队开发系统模块和核心运行时；租户通过配置、自定义字段和受控 Hook 扩展。
2. **业务与会计视图一致：** 尽量避免无必要的“业务单据转会计凭证”中间层；法定财务、税务和审计输出在相应业务阶段另行设计。
3. **数据边界清晰：** 租户、企业、账套、组织、员工、用户、岗位和模块角色不可混为一谈。
4. **低代码不等于无代码：** 常规业务用元数据，复杂业务允许 Kotlin。
5. **简单优先：** 不强制 DDD 四层结构，不为每个业务制造 Model、Service、Repository、Controller 样板。
6. **查询务实：** 复杂查询可以直接 SQL 并返回 JSON，不强制 DTO；但不能绕过权限和数据范围。
7. **核心运行时受控：** 租户 Hook 只能使用平台提供的扩展点和受控 API。
8. **自主可控：** ZTX 自主维护 ztx-ui 和 Design Tokens，不把业务页面绑定到第三方 UI 组件库。
9. **成熟实践优先：** 常规技术机制由项目参考成熟实践确定，不逐项增加产品确认负担。

### 2.3 目标技术方案

以下为当前设计基线；具体依赖版本在 S0 开始前验证稳定性和兼容性，不在 PRD 中提前锁死版本。

| 领域 | 方案 |
|---|---|
| 后端 | Kotlin、Vert.x |
| 数据库 | PostgreSQL |
| 构建 | Gradle Kotlin DSL、Gradle Wrapper、版本目录 |
| 数据库迁移 | Flyway，控制面与租户库分别管理 |
| 前端 | Vue 3、TypeScript、Vite、pnpm |
| 样式 | Tailwind CSS + ZTX Design Tokens |
| 交互原语 | Reka UI |
| 自主组件库 | ztx-ui |
| 组件参考 | shadcn-vue，复制后由 ZTX 自行维护 |
| 图标 | Lucide |
| 表格逻辑 | TanStack Table |
| Hook | 原生 JavaScript；GraalJS 为首选候选，S0 验证兼容性和隔离能力 |
| 缓存 | Caffeine 本地缓存 |
| 可靠事件/任务 | PostgreSQL Outbox 与任务表 |
| 测试 | JUnit 5、Testcontainers、Vitest、Playwright |
| 可观测性 | SLF4J、Logback、Micrometer、OpenTelemetry；Prometheus/Grafana 可选 |

不引入 Redis、Kafka、RabbitMQ、Elasticsearch 作为第一阶段前置依赖。前端静态资源由 Vert.x 提供，生产环境用户只访问一个网址。系统支持离线私有化部署。

## 3. User Stories

### US-01 平台管理员初始化与租户开通

作为平台管理员，我希望通过受控初始化流程建立平台管理身份，并开通租户，以便在不开放公开自助注册的情况下安全管理平台客户。

### US-02 租户管理员初始化

作为平台管理员，我希望开通租户时自动初始化租户业务数据库、基础 Schema、基础元数据和租户初始管理员，以便租户可以安全开始配置。

### US-03 企业和账套管理

作为租户管理员，我希望在一个租户内维护多个企业、多个账套及组织架构，并分别配置数据范围，以便支持集团型企业的不同核算和运营边界。

### US-04 员工、用户和任职管理

作为企业管理员，我希望分别管理员工档案、登录账号和任职关系，以便员工无账号、用户无员工档案，以及一名用户在多个企业任职的情况都能得到正确表达。

### US-05 岗位与模块权限

作为租户管理员，我希望将多个模块角色组合到真实人事岗位，再把岗位分配给员工或用户，以便权限配置与组织岗位保持一致。

### US-06 元数据业务开发

作为平台开发人员，我希望通过元数据定义 DocType、字段、表单、列表和权限，以便快速构建常规业务对象。

### US-07 Document 业务处理

作为业务开发人员，我希望 Document 统一承载常规单据数据、校验、生命周期和业务动作，以便减少重复框架代码。

### US-08 租户自定义字段

作为租户管理员，我希望为允许扩展的 DocType 增加自定义字段，并且字段可以像标准字段一样查询、筛选和排序，以便适应企业差异。

### US-09 租户 Hook 扩展

作为租户管理员，我希望在平台预留生命周期点编写受控 JavaScript Hook，以便增加本租户的业务补充逻辑，而不修改平台核心代码。

### US-10 元数据发布

作为租户管理员，我希望发布元数据时系统检查依赖、迁移数据库结构并生成运行时版本，以便变更可追踪、可回滚且不影响其他租户。

### US-11 工作流和通用服务

作为业务用户，我希望使用统一的审批、编号、文件、通知和导入导出能力，以便不同业务模块获得一致体验。

### US-12 私有化部署和运维

作为实施或运维人员，我希望能够离线安装、升级、备份和诊断 ZTX，以便客户环境不依赖持续公网访问。

## 4. Functional Requirements

### FR-01 工程和部署基座

- 采用 Monorepo 和模块化单体。
- 后端使用 Kotlin + Vert.x，前端使用 Vue 3 + TypeScript。
- API Server 与 Worker 共用代码，按运行角色启动。
- 使用 Docker Compose、Dev Container 和统一开发命令。
- 前端生产构建为静态资源，由 Vert.x 提供。
- 支持离线私有化部署。
- 关键业务规则使用中文注释解释。
- 依赖版本在 S0 进行兼容性验证。

### FR-02 平台管理员和租户开通

- 平台管理员身份存储在控制面数据库，与租户用户身份分离；初期只支持一个平台管理员账号。
- 首次运行且平台管理员不存在时，自动进入初始化向导；仅填写用户名、密码和确认密码，创建成功后自动登录。
- 初始化 API 仅接受服务器本机回环访问；远程部署人员通过 SSH 本地端口转发访问。服务端必须校验连接来源，不得仅依赖前端隐藏入口或未经验证的代理转发头。
- 初始化不生成或要求输入一次性口令；不提供默认管理员密码。初始化成功后 API 永久关闭，服务重启不能重新开放；并发初始化只能创建一个管理员。
- 平台管理员使用独立登录入口、认证 API 和会话；平台与企业工作区共用同一套 App Shell（顶部栏、标签栏、导航框架、页面容器和基础 UI 组件），但菜单、页面内容、标签状态、权限和数据彼此隔离。平台管理员不进入企业业务工作区，不自动获得企业业务数据权限，不提供企业身份切换或模拟登录。
- 平台工作区初期提供平台概览、租户管理、运维管理、账户安全和安全审计。运维管理仅展示 Server/已部署 Worker 状态、数据库连接、版本、启动时间和简要诊断；不提供完整日志检索、远程命令执行、在线服务器配置修改或复杂告警平台。
- 平台管理员密码遗失时，由部署人员通过服务器受控命令重置并审计；不能通过首次初始化重置已有账号。
- MFA 为可选能力，不作为首次初始化或普通用户名密码登录的前置条件；启用 MFA 后才要求相应密钥配置。
- 第一阶段不开放租户公开自助注册。
- 开通租户时自动创建租户业务数据库、Schema、基础元数据和租户初始管理员；企业创建及企业管理员初始化沿用现有流程，本次不调整。
- 租户初始管理员首次登录设置密码。

### FR-03 多租户数据隔离

- 每租户独立 PostgreSQL 业务数据库。
- 控制面数据库保存租户注册、状态、数据库路由和实例信息。
- 浏览器不能指定可信的数据库地址或连接路由。
- 控制面和业务面可以共用后端程序，但连接池、事务和数据访问上下文严格隔离。
- 同一租户内不同企业默认不共享业务数据。
- 不建设跨租户统一身份中心；不同租户的账号、密码、资料、权限和会话相互独立。

### FR-04 企业、账套和组织

- 一个租户可有多个企业，一个企业可有多个账套。
- 组织架构与账套是独立维度，不要求一一对应。
- 组织包括分公司、事业部、部门、工厂等。
- 账套同时承担业务数据隔离和财务核算边界。
- 同一企业基础档案默认共享；账套控制启用状态和使用权限；业务数据和核算规则按账套隔离。
- 数据范围支持租户级、企业级、账套级，并结合部门、工厂等任职范围执行。
- 集团档案由集团管理员维护；企业按需申请/启用，并可维护本地补充字段。
- 修改或停用集团档案前检查引用，不破坏历史数据。
- 企业间协同使用双方独立单据和关联关系；一方不得直接修改另一方数据；接收方确认后才形成自己的正式数据。

### FR-05 员工、用户和任职

- Employee 与 User 独立建模，通过关联关系连接。
- 员工可以无账号，用户可以无员工档案。
- Employment 保存企业、部门、岗位、任职范围和任职期限，并保留历史。
- 同一租户用户可关联该租户内多个企业的员工档案。
- 不跨租户关联自然人身份。

### FR-06 岗位、模块角色和权限

- Position 是真实人事岗位，也是权限组合载体。
- 用户可担任多个岗位，岗位任职范围可限定企业、账套、部门、工厂。
- 各业务模块独立维护模块角色；不同模块允许同名角色。
- 一个岗位组合多个模块角色。
- 模块角色配置功能权限、数据权限和字段权限。
- 多岗位权限按并集合并；显式禁止优先于允许。
- 合并后的数据范围仍受任职范围约束。
- 字段权限支持可见、编辑、只读、隐藏和脱敏。
- Ability Runtime 在服务端统一执行权限检查。
- API、查询、列表、导出、文件访问均不得绕过权限。

### FR-07 元数据和 Document

- 元数据支持 DocType、字段、默认值、必填、只读、引用关系、表单布局、列表列、筛选、排序、搜索和权限声明。
- Document 同时承载常规业务数据和行为，支持保存、提交、撤销、作废、生命周期事件和下游单据生成。
- 支持三种开发模式：纯元数据；元数据 + Kotlin 单业务文件；Kotlin 专用实现。
- 默认一个业务一个文件，不强制 Model、Service、Repository、Controller 四层。
- 复杂制造计算、成本结算、排程等允许 Kotlin 专用实现。
- 业务动作具有明确名称和权限，不将所有业务塞入生命周期 Hook。

### FR-08 查询和 API

- 查询允许直接 SQL，结果可直接返回 JSON，不强制 DTO。
- SQL 使用参数化方式，禁止拼接不可信输入。
- 查询不强制经过 DDD 分层或 Document 生命周期。
- 所有查询必须执行租户、企业、账套、组织、功能和字段权限检查。
- API 提供稳定错误码和统一错误结构。
- API 契约通过 OpenAPI 描述；元数据结构按需使用 JSON Schema。

### FR-09 自定义字段

- 自定义字段存储于独立扩展表，不修改标准业务表。
- 每个自定义字段对应一个独立 PostgreSQL 物理列。
- 明确不采用 JSONB 集合存储和 EAV 多行属性存储。
- 每个 DocType 对应自己的自定义扩展表；表头和明细分别管理扩展字段。
- 扩展列使用 PostgreSQL 原生类型，支持 SQL 查询、筛选、排序、统计和索引。
- 物理列名由平台生成并管理，不直接使用用户输入作为 SQL 标识符。
- 新增、修改、删除和类型变更通过元数据发布与数据库迁移完成。
- 结构变更必须检查现有数据，禁止静默丢失数据。
- 自定义字段权限与标准字段使用统一权限机制。

### FR-10 元数据发布和 RuntimeSnapshot

- 发布时根据依赖闭包生成 Release Bundle。
- 区分平台基础元数据与租户级元数据。
- 未变对象可继续引用旧版本。
- 发布生成运行时执行计划，覆盖字段、布局、权限、生命周期、关系和查询配置。
- 每个请求开始时固定使用一个 RuntimeSnapshot。
- 发布只影响目标租户。
- 多实例加载新版本后报告 READY，达到激活条件后统一切换。
- 发布失败保留旧版本；支持版本回滚。
- 破坏性迁移需审批，优先使用 Expand-Contract。
- 普通缓存刷新与 RuntimeSnapshot 发布协调分开治理。

### FR-11 Hook 扩展

- 租户管理员可以编写原生 JavaScript Hook。
- Hook 只能注册平台预留生命周期点并调用受控 API。
- 禁止任意 SQL、任意 JVM 访问及覆盖核心库存扣减、成本计算、提交逻辑。
- Hook 代码保存在 PostgreSQL，与 Kotlin 源码和部署包分离。
- Hook 支持版本、发布记录、API 版本、隔离、资源限制和审计。
- 保存前、提交前 Hook 同步执行；失败时当前事务回滚。
- 保存后、提交后 Hook 通过可靠事件异步执行，支持重试。
- 外部 HTTP、邮件等副作用不参与数据库事务。
- GraalJS 为首选运行时候选，S0 必须验证 JDK/Vert.x 兼容性、安全隔离和资源限制；验证不通过时不得降低安全要求强行上线。

### FR-12 工作流

- 普通单据支持元数据驱动工作流。
- 支持流程定义和版本、流程实例、审批节点、审批人规则、转交、加签、退回和审批历史。
- 复杂制造流程允许 Kotlin 实现。
- 流程操作必须执行权限和审计。

### FR-13 编号服务

- 支持前缀、日期、流水号以及企业、账套、工厂等编号范围。
- 支持自动编号和手工编号。
- 编号规则变化不重新生成历史编号。
- 并发取号不得产生重复编号。

### FR-14 文件服务

- 文件服务独立于业务模块。
- 第一阶段文件二进制存本地磁盘，数据库保存元数据和业务关联。
- 支持权限、版本和审计。
- 存储接口可扩展至对象存储。
- 文件下载和预览必须执行权限检查。

### FR-15 通知中心

- 第一阶段提供站内通知、未读/已读、模板和用户偏好。
- 邮件、企业微信等外部渠道不属于第一阶段交付。
- 通知异步发送应具备可靠重试和幂等机制。

### FR-16 导入导出

- 支持 Excel 和 CSV。
- 导入支持模板、字段映射、校验、错误报告和批量处理。
- 导入数据校验后由用户确认执行。
- 导出执行字段权限和数据范围检查。
- 大批量处理通过后台任务执行并提供状态查询。

### FR-17 缓存、Outbox 和后台任务

- 使用 Caffeine 本地缓存，不引入 Redis。
- 多实例普通缓存失效通过 PostgreSQL Outbox/可靠事件通知各实例刷新。
- RuntimeSnapshot 发布协调独立管理。
- 第一阶段使用 PostgreSQL Outbox 和任务表，不引入 Kafka/RabbitMQ。
- 后台任务支持状态、执行记录、幂等、重试、错误追踪和必要的人工干预。

### FR-18 搜索、审计、可观测性和国际化

- 第一阶段使用 PostgreSQL 搜索，不引入 Elasticsearch。
- 关键业务操作和配置变更记录审计主体、时间、对象、动作、结果及必要变更信息。
- 日志采用 SLF4J + Logback；指标采用 Micrometer；链路追踪采用 OpenTelemetry。
- Prometheus/Grafana 可作为可选部署组件。
- 第一阶段支持简体中文和英文。
- 支持用户语言、企业时区偏好，以及日期、时间、数字和货币本地化。
- 错误码稳定，前端根据语言映射消息。
- 日志和追踪不得泄露密码、令牌及不必要的敏感业务数据。

### FR-19 前端和设计系统

- 采用 Vue 3、TypeScript、Vite、pnpm。
- Tailwind CSS 作为样式基础；通过 ZTX Design Tokens 统一颜色、字号、间距、圆角等。
- Reka UI 提供无样式交互原语。
- shadcn-vue 仅作为组件代码参考/来源，复制到项目后由 ZTX 自行维护。
- ztx-ui 是业务页面使用组件的统一入口；业务页面不直接绑定第三方组件库。
- Lucide 作为统一图标来源。
- TanStack Table 提供表格逻辑。
- 字体建议：Noto Sans SC、Inter、JetBrains Mono；字体资源本地部署并提供系统字体回退，不依赖在线 CDN。
- 视觉风格：现代企业软件、制造业专业感、高信息密度、克制、适度紧凑；以暖色中性色为基础，避免大量留白。
- 参考字号：页面标题 18px、区块标题 15px、正文 14px、表格 13px、辅助信息 12px；图标 16–18px；4px 间距基准；按钮/输入框约 32–36px；表格行约 36–40px。最终以视觉验收为准。
- 全局 Tab 位于最顶部；右上角仅全屏、通知和用户图标。
- 列表和表单不增加重复标题行；列表页不显示详情 Tab。
- 表单操作工具位于底部。
- 列表操作行紧凑，新建位于操作行右侧；支持批量操作、导出和更多操作；筛选和排序入口位于右侧。
- 分页行左侧显示总记录数和已选数量。
- 导航支持三级菜单；按日常工作、单据查询、报表分析等组织；日常工作采用悬停弹出功能菜单，避免过长嵌套下拉。
- ztx-ui 至少覆盖 Button、Input、Select、Checkbox、Radio、DatePicker、Dialog、Drawer、Dropdown、Tabs、Tooltip、Form、Table、Pagination、Tree、Upload、Notification、Menu，并逐步提供 ERP 专用组件。
- Monorepo 内包统一版本、构建和测试，不要求独立发布。

## 5. Acceptance Criteria

### AC-01 初始化与开通

- 首次运行自动进入平台管理员初始化向导，仅填写用户名、密码和确认密码，创建成功后自动登录。
- 初始化 API 仅允许服务器本机回环访问；远程部署人员通过 SSH 本地端口转发使用；公网非回环请求必须被服务端拒绝。
- 不使用一次性初始化口令，不存在代码或镜像内置的通用管理员密码。
- 并发初始化只能创建一个平台管理员；初始化成功后接口永久关闭，重启不能重新开放。
- 平台管理员可登录平台管理工作区；平台与企业工作区共用统一 App Shell，但菜单、页面内容、标签状态、认证会话和路由权限相互隔离。
- 平台管理员不自动获得企业业务数据权限，不能切换或模拟企业用户。
- 平台工作区包含平台概览、租户管理、运维管理、账户安全和安全审计；企业创建及企业管理员初始化流程保持现状。
- 运维管理显示 Server、已部署 Worker、数据库连接状态、版本、启动时间和简要诊断；不提供远程命令、完整日志检索或在线服务器配置修改。
- 租户开通后数据库、Schema、基础元数据和初始管理员均已就绪。

### AC-02 租户隔离

- 租户 A 的身份凭据不能访问租户 B 的业务数据。
- 即使请求伪造租户标识，也不能改变服务端确定的数据库路由。
- 控制面事务不能误用租户业务连接，租户业务事务不能误用控制面连接。
- 跨租户账号、会话和权限互不继承。

### AC-03 组织与权限

- 一个租户可建立多个企业，一个企业可建立多个账套。
- 组织单元与账套可独立配置关联。
- 用户可关联多个企业员工档案；员工可没有账号。
- 用户担任多个岗位后获得岗位组合的模块角色。
- 多岗位授权按并集合并，显式禁止优先于允许。
- 最终数据范围不得超出岗位任职范围。
- 无权限用户通过 API、SQL 查询入口、导出或文件 URL 均不能访问受限数据。

### AC-04 Document 与元数据

- 仅通过元数据可创建简单业务对象并生成基础表单和列表。
- 普通单据可用一个 Kotlin 业务文件定义强类型数据和常规行为。
- 嵌套 JSON 明细可正确转换为 Kotlin 强类型集合。
- Document 生命周期按定义执行，失败事务行为一致。
- 复杂查询可直接 SQL 返回 JSON，但仍执行权限检查。

### AC-05 自定义字段

- 新增自定义字段后，对应扩展表出现独立物理列。
- 不修改标准业务表结构。
- 字段类型映射为正确的 PostgreSQL 类型。
- 可按自定义字段筛选、排序和查询，并可按需建立索引。
- 字段新增、类型变更和删除通过迁移执行。
- 迁移失败时旧版本仍可运行，已有数据不被静默破坏。
- 表头与明细扩展字段分别正确关联业务记录。

### AC-06 元数据发布

- 发布前检查依赖闭包和元数据合法性。
- 发布产生可追溯版本和 RuntimeSnapshot。
- 同一请求不会混用两个 RuntimeSnapshot。
- 多实例全部满足 READY 条件后才按协调策略激活。
- 发布失败保留旧版本；可回滚到已知可用版本。
- 破坏性迁移未审批时不能执行。

### AC-07 Hook

- Hook 只能调用授权 API 和允许的生命周期点。
- Hook 无法直接执行任意 SQL 或访问任意 JVM 能力。
- 同步 Hook 失败时当前事务回滚。
- 异步 Hook 通过可靠事件执行，失败可重试且具备幂等保护。
- Hook 超时或超出资源限制时被终止并记录审计信息。
- GraalJS 安全隔离未通过验证时不得进入生产启用状态。

### AC-08 通用服务

- 工作流可以定义、启动、审批、转交、加签、退回并保留历史。
- 并发编号请求不会产生重复编号。
- 文件访问执行权限检查。
- 导入必须先校验再确认执行；导出执行字段和数据范围权限。
- Outbox 事件和后台任务支持可靠重试及幂等。

### AC-09 前端体验

- 业务页面统一通过 ztx-ui 使用基础组件。
- Design Tokens 能统一控制主要视觉属性。
- 页面遵循顶部 Tab、紧凑列表操作行、底部分表单操作和三级导航规范。
- 主要表单、列表、弹窗和菜单具备键盘操作及可访问性基础。
- 生产部署不依赖外部字体 CDN 或在线组件资源。

### AC-10 工程和质量

- 新开发环境可按文档完成启动。
- 后端核心集成测试使用真实 PostgreSQL（Testcontainers）。
- 前端组件和逻辑有 Vitest 测试。
- 核心用户流程有 Playwright 测试。
- CI 可重复执行格式检查、构建和测试。
- 日志、指标和链路追踪可关联请求和必要的租户上下文。

## 6. BDD Scenarios

### BDD-01 平台管理员首次初始化

**Given** 系统尚未创建平台管理员  
**When** 部署人员在服务器本机访问，或通过 SSH 本地端口转发打开初始化向导，并提交用户名、密码和确认密码  
**Then** 系统创建唯一的平台管理员并自动建立登录会话  
**And** 初始化接口永久关闭  
**And** 非回环请求、并发重复初始化及服务重启后的再次初始化均被拒绝

### BDD-02 租户开通

**Given** 平台管理员已登录控制面  
**When** 平台管理员提交合法的租户开通请求  
**Then** 系统创建该租户独立业务数据库  
**And** 执行数据库迁移并初始化基础元数据  
**And** 创建租户初始管理员  
**And** 其他租户的数据和账号不受影响

### BDD-03 伪造租户上下文

**Given** 用户已登录租户 A  
**When** 用户在请求中伪造租户 B 的标识或数据库地址  
**Then** 服务端仍按可信认证上下文和控制面路由处理  
**And** 用户不能访问租户 B 的数据

### BDD-04 多岗位权限合并

**Given** 用户在同一任职范围内担任多个岗位  
**And** 这些岗位组合了不同模块角色  
**When** 用户访问某项业务功能  
**Then** 系统按权限合并规则计算有效权限  
**And** 显式禁止优先于允许  
**And** 数据范围不超过任职范围

### BDD-05 自定义字段发布

**Given** 租户管理员为采购订单定义一个自定义字段  
**When** 管理员发布该元数据版本  
**Then** 系统在采购订单自定义扩展表创建对应物理列  
**And** 标准采购订单表结构不被修改  
**And** 该字段可以被查询、筛选和排序

### BDD-06 自定义字段迁移失败

**Given** 当前版本的自定义字段结构正在正常使用  
**When** 新版本数据库迁移失败  
**Then** 新版本不能激活  
**And** 当前有效 RuntimeSnapshot 保持可用  
**And** 系统记录失败原因和迁移状态

### BDD-07 Document 提交前校验失败

**Given** 用户正在提交一张 Document  
**And** 提交前校验或同步 Hook 执行失败  
**When** 提交请求结束  
**Then** 本次事务回滚  
**And** 单据保持提交前状态  
**And** 失败原因可被追踪

### BDD-08 异步 Hook 重试

**Given** Document 已成功提交并产生可靠事件  
**When** 异步 Hook 第一次执行失败  
**Then** 系统根据重试策略重新执行  
**And** 重复投递不会造成重复业务副作用  
**And** 最终执行状态可查询

### BDD-09 RuntimeSnapshot 请求一致性

**Given** 租户有一个已激活的 RuntimeSnapshot  
**When** 新版本发布并切换期间有请求正在执行  
**Then** 已开始请求继续使用其固定快照  
**And** 新请求使用切换后生效的快照  
**And** 单次请求不混合两个版本

### BDD-10 导出权限

**Given** 用户只能查看部分字段和部分组织数据  
**When** 用户执行列表导出  
**Then** 导出结果只包含有权访问的数据和字段  
**And** 不得通过导出绕过页面权限

### BDD-11 平台管理工作区与企业工作区隔离

**Given** 平台管理员已登录  
**When** 打开平台管理路由  
**Then** 系统显示与企业工作区共用的统一 App Shell，并只显示平台管理菜单和页面  
**And** 平台与企业的标签状态、认证会话和路由权限彼此隔离  
**And** 不显示企业业务菜单或企业数据，平台管理员不能通过该会话进入企业业务工作区

### BDD-12 平台运维基础诊断

**Given** 平台管理员已登录平台管理工作区  
**When** 查看运维管理  
**Then** 系统显示 Server、已部署 Worker、数据库连接、版本和启动时间等状态  
**And** 异常时显示简要诊断信息  
**And** 页面不提供远程命令执行或完整日志检索

## 7. Design Decisions

### 7.1 数据与模块边界

- 控制面数据库与租户业务数据库分离。
- 每租户独立业务数据库。
- 租户内企业、账套和组织为独立模型。
- Employee、User、Employment、Position 和模块 Role 分别建模。
- 库存管理和成本管理保持独立模块边界；批次实际成本、后续成本结算和历史追溯属于后续制造业务设计约束。

### 7.2 业务开发模型

- 默认一个业务一个文件，不强制四层架构。
- Document 承载常规单据数据和行为。
- 元数据描述通用结构和界面。
- 复杂制造算法由 Kotlin 专用实现。
- 查询可以直接 SQL，但权限必须在服务端统一执行。

### 7.3 自定义字段物理模型

- 每个 DocType 一张自定义扩展表。
- 每个自定义字段一个独立物理列。
- 表头与明细分开。
- 不使用 JSONB 字段集合或 EAV。
- 具体 PostgreSQL 类型映射、列名生成、索引策略和 DDL 迁移策略在 S2 详细设计中确定。

### 7.4 元数据运行时

- 发布构建 Release Bundle 和运行时执行计划。
- RuntimeSnapshot 在请求开始时固定。
- 多实例发布使用 READY 协调。
- 版本回滚和数据库迁移分开治理，不能仅回滚元数据而忽略数据结构兼容性。

### 7.5 Hook 运行时

- JavaScript 是租户 Hook 的第一阶段语言。
- GraalJS 为首选候选，但必须在 S0 验证兼容性、隔离和资源限制。
- Hook 不拥有任意数据库或 JVM 权限。
- 同步 Hook 参与当前事务；异步 Hook 使用 Outbox。

### 7.6 缓存和可靠事件

- Caffeine 本地缓存。
- PostgreSQL Outbox 负责可靠事件通知和多实例普通缓存刷新。
- RuntimeSnapshot 激活协调不等同于普通缓存失效。
- 第一阶段不引入 Redis、Kafka 或 RabbitMQ。

### 7.7 前端组件体系

- Tailwind CSS 负责样式基础。
- Reka UI 负责无样式交互原语。
- shadcn-vue 作为代码参考，不作为运行时强绑定依赖。
- ztx-ui 是唯一面向业务页面的基础组件入口。
- Lucide 提供统一图标，TanStack Table 提供表格逻辑。
- 通过 Design Tokens 保持 ZTX 自己的暖色、高密度、专业企业软件视觉。

### 7.8 部署和运行

- 模块化单体，不以微服务作为当前目标。
- API Server 和 Worker 共用代码、按角色启动。
- PostgreSQL 同时承担业务数据、Outbox 和初期任务队列。
- Vert.x 提供 API 和前端静态资源。
- 离线私有化部署是产品要求，不是可选后补能力。

## 8. Non-functional Requirements

### 8.1 安全

- 密码采用安全哈希存储。
- 平台管理员 MFA 为可选能力，未启用时不阻断首次初始化或普通用户名密码登录。
- 租户路由由服务端可信上下文决定。
- 权限在服务端统一执行。
- Hook 必须隔离并限制资源。
- 文件、导入导出和后台任务执行权限检查。
- 敏感配置和密钥不得写入仓库或日志。

### 8.2 数据一致性与并发

- 业务操作明确事务边界。
- 提交、撤销和关键状态变更必须保证并发安全。
- Outbox 与业务数据在同一事务中写入。
- 异步消费者必须幂等。
- 编号并发生成不能重复。
- 元数据发布失败不能破坏当前有效版本。
- 结构迁移必须考虑旧版本兼容和数据保护。

### 8.3 可用性和可靠性

- 提供健康检查和就绪检查。
- 后台任务失败可追踪、重试和人工处理。
- 多实例普通缓存失效可恢复。
- 元数据发布具备失败恢复和回滚能力。
- 私有化部署提供升级、备份和恢复操作说明。

### 8.4 性能与扩展

- 常规列表查询支持筛选、排序、分页。
- 自定义字段可使用独立列和索引。
- 查询可直接 SQL，避免不必要的对象映射开销。
- Caffeine 缓存热点元数据和运行时对象。
- 具体性能目标在 S0 建立基准后，按业务规模制定，不在缺乏基准时编造数值。

### 8.5 可维护性

- 模块职责和数据归属清晰。
- 不强制固定四层代码结构。
- 核心业务规则有中文注释和自动化测试。
- 统一开发、构建、测试和部署命令。
- 版本和迁移可追溯。
- 代码结构适合人类和 AI 阅读、修改及测试。

### 8.6 国际化与部署环境

- 简体中文和英文。
- 用户语言、企业时区、日期时间和数字货币本地化。
- 字体及前端依赖可离线部署。
- 不依赖公网 CDN 才能正常运行。

## 9. Out of Scope

以下不属于平台基座 S0–S3 的交付范围：

- 完整 BOM 管理。
- MRP 运算。
- 工艺路线和生产排程。
- 车间执行管理。
- 完整采购、销售、库存和财务业务模块。
- Android/iOS 移动端。
- 跨租户统一身份中心。
- Redis、Kafka、RabbitMQ、Elasticsearch。
- 租户自行开发全新系统模块。
- 租户直接修改平台核心运行时。

## 附录 A：实施阶段边界

### S0：工程基础与平台启动

- 依赖版本和 GraalJS 候选方案兼容性验证。

**阶段验收：** 新环境可启动；平台管理员可登录并开通租户；租户管理员可首次登录；健康检查和基础 CI 通过。

- 租户、企业、账套、组织。

- Position、模块角色。
- 功能、数据、字段权限。
- Ability Runtime。
- 基础审计。

**阶段验收：** 多租户隔离成立；企业和账套边界正确；多岗位授权、显式拒绝和数据范围约束通过自动化测试。

**阶段验收：** 租户可在受控边界内扩展业务行为；通用平台服务可用；核心流程和故障场景自动化测试通过。

## 附录 B：需求追溯和变更规则

- 用户明确确认的产品边界优先于 AI 的实现建议。
- 代码库现状是事实来源，但现有实现不自动等于正确需求。
- 未确认的技术细节必须标记为建议或待验证，不得伪装成用户已确认决策。
- 涉及租户隔离、权限、安全、数据模型、事务边界或兼容性破坏的变更必须记录影响。
- 常规技术实现优先采用成熟实践，不为细枝末节反复打断产品确认。
- PRD 审核通过后才进入 prd-to-issues；Issue 拆分不得擅自改变本 PRD 的产品边界。
